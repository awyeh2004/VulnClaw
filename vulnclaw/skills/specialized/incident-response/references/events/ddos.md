# DDoS 攻击应急响应

**核心问题不是"怎么找 webshell"，而是"服务为什么不可用、攻击流量从哪来、怎么缓解、要不要报案"。**
DDoS 是唯一一类**攻击者不在目标机器上留文件**的事件 —— 前几篇的排查套路（找落地文件、
找持久化、找后门账号）在这里基本失效，必须换成流量视角。

**主流程**：`初步预判 → 判断攻击类型 → 缓解 → 溯源与留证 → 加固`

> 本篇编排依据出题方教材第 8 章（`book/ch8-ddos-guide.md`）。

---

## 一、⭐ 先分清"是 DDoS"还是"像 DDoS"

DDoS 的判据是**流量特征**，不是主机特征。四条线索（教材 8.3.1）：

| 线索 | 看什么 |
|---|---|
| ① 安全/流量设备告警 | 异常时间段内出现**大量与业务无关**的数据包（如源端口 123/53 的 UDP） |
| ② 安全设备告警内容 | 攻击类型、协议、流量大小 |
| ③ 服务/页面请求打满 | 网页打不开或极慢 → 查 **Web 访问日志统计**，看是否有某个页面/JS 访问量异常 |
| ④ ⭐ **大量等待中的 TCP 连接** | 与恶意 IP 的异常连接，或连接数异常膨胀 |

⭐ **第 ④ 条是最能自己动手验证的一条** —— 没有流量设备时靠它：

```bash
# 连接状态分布：SYN_RECV 堆积 = SYN Flood；ESTABLISHED 暴涨 = 连接耗尽
ss -s
netstat -ant | awk '{print $6}' | sort | uniq -c | sort -rn
# 按源 IP 统计连接数 Top（找攻击源/僵尸网络成员）
netstat -ant | awk '{print $5}' | cut -d: -f1 | sort | uniq -c | sort -rn | head -20
ss -ant | awk 'NR>1 {print $5}' | cut -d: -f1 | sort | uniq -c | sort -rn | head -20
```

### ⚠️ 别把这三件事误判成 DDoS

| 现象 | 可能真因 |
|---|---|
| CPU/负载高、服务慢 | **挖矿木马**（见 `events/cryptomining.md`）—— 先看是否连矿池 |
| 服务不可用但流量不大 | 服务自身崩溃、磁盘满、依赖的下游挂了、被植入后门拒绝服务 |
| 大量请求来自单一 IP | 不是分布式 —— 那是单点 CC/爬虫，处置方式不同 |

> 教材 8.1.4 专门讲"攻击中的一些误区"，核心一条：**DDoS 无法彻底解决**，
> 增带宽是**退让策略**而不是防护。别在报告里承诺"已根治"。

## 二、判断攻击类型（决定缓解手段）

按**消耗什么资源**分三类（教材 8.1.3）：

### 消耗网络带宽资源

| 类型 | 特征 |
|---|---|
| **ICMP Flood** | 大量 ICMP 请求（`ping` 洪泛） |
| **UDP Flood** | ⭐ 目前主流。**小包**（64B，包数多、设备检查压力大）或**大包**（>MTU 1500B，需分片重组，耗带宽+设备性能） |
| **反射/放大（DRDoS）** | ⭐ 攻击者**伪造受害者源 IP** 向"反射器"（开放 DNS/NTP/SNMP/chargen 等）发请求，反射器把响应打给受害者。**同时隐藏了攻击源** |

⚠️ **反射放大是最容易误判的一类**：受害机看到的源 IP 是**无辜的第三方反射器**，
不是攻击者。教材案例里的线索就是**源端口 123（NTP）/ 53（DNS）的 UDP 报文** ——
看到这两个源端口要立刻想到反射放大。

### 消耗系统资源 / 应用资源

- **SYN Flood**：大量半开连接占满连接表（`SYN_RECV` 堆积）
- **CC 攻击**：请求本身合法但量极大，打满应用（如动态查询、登录接口）
- **慢速攻击**：Slowloris 之类，连接数不多但长期占住

### 判断方法（没有专业设备时）

```bash
# ① 抓包看协议分布（装了 Wireshark 就有 tshark / dumpcap）
tshark -i any -a duration:30 -q -z io,phs          # 协议分层，看谁占大头
tshark -i any -a duration:30 -q -z conv,ip         # IP 会话排行，看攻击源分布

# ② 按源端口看（反射放大的关键线索）
tshark -i any -a duration:30 -Y "udp" -T fields -e udp.srcport | sort | uniq -c | sort -rn | head

# ③ 已有的 pcap（离线分析更稳，见 50-memory-traffic.md）
tshark -r attack.pcap -q -z io,phs
tshark -r attack.pcap -q -z conv,ip | head -30
```

> ⭐ **离线 pcap 优先**：现场抓包会加重负载，而且流量随时变化。
> 有 pcap 就先固化下来再分析 —— 见 `references/50-memory-traffic.md` 第三节。

## 三、缓解处置（顺序）

教材 8.2.2 + 8.3.3：

| 顺序 | 动作 | 说明 |
|---|---|---|
| 1 | **限制访问速率 / 调整安全设备策略** | 确认攻击类型后才做，别盲目封 |
| 2 | **封堵异常 IP** | 依据设备记录。⚠️ 反射攻击下封源 IP = **封掉无辜反射器**，要看清楚 |
| 3 | **联系运营商流量清洗** | 流量远超出口带宽时**这是唯一有效手段** |
| 4 | **保留证据 + 报案** | 见下节 —— 这一步容易被漏 |

⚠️ **封 IP 的两个坑**：
- 反射放大场景（源端口 53/123）封源 IP 打不到攻击者，反而可能封掉公共服务
- 僵尸网络 IP 数量庞大，逐条封堵不可持续 —— 该做的是**特征封堵**（协议/端口/包长特征）

## 四、⭐ 留证与溯源（最容易被忽略的必要步骤）

教材 8.2.3 明确说：**遭遇攻击时应保留相关证据，及时报案。**
而且它也承认 **僵尸网络导致溯源挑战很大** —— 所以别把报告写成"已溯源到攻击者"。

**必须固化的证据**（攻击流量是**转瞬即逝**的，服务一恢复就没了）：

```bash
# 1) 抓包（限时长，别把磁盘写满）
tshark -i any -a duration:60 -w /tmp/ddos-$(date +%s).pcap
# 或 dumpcap（同样的东西，更轻）
dumpcap -i any -a duration:60 -w /tmp/ddos.pcap

# 2) 连接快照（多抓几次，看变化）
ss -ant > /tmp/conn-$(date +%s).txt
cat /proc/net/tcp /proc/net/tcp6 > /tmp/procnettcp-$(date +%s).txt

# 3) 相关日志（Web 访问日志是教材点名的判据来源）
tail -n 5000 /var/log/nginx/access.log > /tmp/web-access-snapshot.txt
# 统计请求量 Top 的 URL 与 IP
awk '{print $1}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head -20
awk '{print $7}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head -20

# 4) 安全设备/负载设备的告警与日志（教材案例的关键证据）
#    负载日志、内存告警、重启时间 —— 这些常是定位真因的突破口
```

**报告里必须区分**：`[观测]` 抓到的流量特征 → `[推断]` 攻击类型 → `[知识]` 该类攻击的一般原理。
**不要把"源 IP 是 X"写成"攻击者是 X"** —— 反射攻击和僵尸网络下这个推断是错的。

## 五、加固建议（教材 8.2.4）

**服务器防护**
- 非业务端口**不对公网开放**（减少暴露面）
- 及时打补丁，**避免服务器沦为"肉鸡"**（即：先确认自己不是攻击源）
- ⭐ 教材 8.1.5 第 7 条：**对服务器定期排查，防止其被攻击利用成为攻击者的工具**

**网络防护与安全监测**
- 优化网络、**负载分流**，避免单点故障
- 限制同时打开的最大连接数
- 部署流量监控 / 抗 DDoS 设备，**为溯源提供基础**

**应用系统防护**
- 应用代码性能优化（降低 CC 攻击的性价比）

> ⭐ 教材案例里的真实教训：DDoS 停止后**大量业务流量涌向存在单点故障的负载设备**，
> 导致内存告警 → 设备重启。**攻击的次生影响（架构脆弱点）往往比攻击本身更致命**，
> 排查时要看攻击前后的**设备状态变化**，不只盯流量。

## 六、常见问法与答法

| 问法 | 答法要点 |
|---|---|
| 如何判断是哪种 DDoS？ | 按**消耗的资源**分：带宽（ICMP/UDP/反射放大）、系统（SYN Flood）、应用（CC）。**源端口**是反射放大的关键线索 |
| 为什么封 IP 没用？ | 反射放大下源 IP 是**无辜反射器**；僵尸网络 IP 海量。要按**特征**封（协议/端口/包长） |
| 流量远超带宽怎么办？ | **联系运营商流量清洗** —— 这是唯一有效手段。增带宽是退让策略 |
| 能溯源到攻击者吗？ | 教材明确说**僵尸网络导致溯源挑战大**。能做的是留证 + 报案，别承诺溯源结果 |
| 现场第一件事做什么？ | ⭐ **抓包固化**（限时长）+ 连接快照。攻击流量转瞬即逝，服务一恢复证据就没了 |
| 攻击停止了就结束了吗？ | 不是 —— 要看**次生影响**（负载/内存/重启），以及确认自己**没被当成肉鸡** |
