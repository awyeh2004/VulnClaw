# 数据泄露应急响应

**这类事件的特点：数据不在你的机器上 —— 已经在外面流传了。** 所以排查目标不是
"主机被怎么入侵"，而是 **"数据从哪条路径出去的"**，以及**留证与对外口径**。

**主流程**：`发现 → 梳理基本情况 → 判断泄露途径 → 逐路径排查 → 处置与留证 → 报告`

> 本篇编排依据出题方教材第 9 章（`book/ch9-datalleak-guide.md`）。

---

## 一、⭐ 先判"数据是怎么被发现的"——它决定后续路径

教材 9.2.1 列了三种发现方式，**每种对应不同的排查重点**：

| 发现方式 | 典型迹象 | 排查重点 |
|---|---|---|
| **外部反馈** | 互联网披露、客户投诉、第三方机构通告 | 数据已在小范围流传 → 重点查**外传路径**与**谁有权限** |
| **监管通报** | 执法/监管机构通报 | 一般是**大量个人隐私数据** → 重点查**合规**与**存储位置** |
| **自行发现** | 内部敏感信息出现在互联网、有流传迹象 | 重点查**内部人员**与**终端** |

⚠️ **别一上来就查服务器。** 数据显示"数据已经出去了"时，**外传路径**比入侵痕迹更重要。

---

## 二、⭐ 泄露途径全景（按这个清单逐条排除）

教材 9.1.2 把途径分成**外部泄露**和**内部泄露**两大类 —— 这份清单是排查的主框架：

### 外部泄露（数据经非自身系统泄露）

| 子类 | 具体形态 |
|---|---|
| **供应链泄露** | ① **自身供应链**：物流、仓储、支付系统等含大量敏感信息的系统被入侵<br>② **第三方供应商**：代码仓库、外包人员服务、第三方 SaaS 被入侵，或供应商**为牟利主动泄露** |
| **互联网敏感信息泄露** | ① **搜索引擎**（违规把敏感数据传上公开网站被收录）<br>② ⭐ **公开代码仓库**（GitHub / Gitee —— 研发运维违规上传）<br>③ **网盘**（未加密敏感数据上传并分享）<br>④ **社交网络**（违规或无意识披露） |
| **互联网应用系统泄露** | 商城 / VPN / 邮件系统等的**未授权访问、数据遍历、管理弱密码、SQL 注入** |

⚠️ ⭐ **"互联网敏感信息泄露"这一类最容易被忽略，也最容易查**：它不是"被攻击"，
而是**自己人违规放出去的**。排查成本极低（去 GitHub/网盘搜一下就有结论），
但如果不查，会把整份报告引向错误方向。

### 内部泄露（数据经自身系统泄露）

| 子类 | 具体形态 |
|---|---|
| **内部人员窃密（主动）** | 客服 / 研发运维 / 数据运营等**用自身权限获取并转售** |
| ⭐ **终端木马窃取** | 办公终端被控：**来历不明的 U 盘、盗版软件、钓鱼邮件** |
| **基础支撑平台泄露** | ES / Redis / 数据仓库等基础平台**被攻击**（往往无鉴权就暴露） |
| **内部应用系统泄露** | 内部业务系统的未授权访问 / 数据遍历 / 弱密码 / SQL 注入 |

---

## 三、判断途径的推理规则（教材 9.2.3）

教材给了两条**很实用的经验判据**：

| 若…… | 则很可能是…… |
|---|---|
| 泄露数据**存储在互联网可访问的服务器**，且业务系统**未经过专业的上线安全评估** | **外部人员非法入侵** |
| 泄露数据**存储在内部网络**，且**仅有少部分管理员能访问**，内部网络安全良好 | **内部人员恶意披露** 或 **未授权访问窃取** |

⭐ **但教材也明确说**：这两种典型之外，很多事件要靠 **Web 访问日志 + 系统日志 + 内网安全态势**
综合分析才能定位。**别把这两条规则当结论用。**

## 四、逐路径排查（实操）

### 4.1 先做"低成本高命中"的三项

```bash
# ① 公开代码仓库泄露（最快能出结论的一项）
#   GitHub / Gitee 搜：公司域名、内部系统名、数据库连接串、密钥前缀
#   本地也查一遍 git 历史里有没有误提交后删除的敏感文件
git log --all --diff-filter=D --name-only | grep -iE 'config|key|secret|\.env|password'
git log -p --all -S 'BEGIN RSA PRIVATE KEY' --oneline | head
git log -p --all -S 'password' --oneline | head -20

# ② 网盘/对象存储是否对外可读
#   对象存储未授权访问是最常见的云侧泄露
curl -s -o /dev/null -w '%{http_code}\n' 'https://<bucket>.oss-cn-xxx.aliyuncs.com/'
# 200 = 匿名可列目录，这就是泄露源

# ③ 基础支撑平台是否裸奔（ES / Redis 是重灾区）
curl -s 'http://<host>:9200/_cat/indices?v' | head    # ES 无鉴权
redis-cli -h <host> ping                              # Redis 无鉴权
```

### 4.2 服务器侧（若怀疑外部入侵）

```bash
# Web 访问日志：找异常访问模式（教材点名的判据来源）
# ① 访问量 Top 的 IP / URL
awk '{print $1}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head -20
awk '{print $7}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head -20

# ② ⭐ 大批量取数据的特征：同 IP 高频访问"明细/列表/导出"类接口
grep -E '/(list|detail|export|download|api/v[0-9]+/(order|user|member))' \
    /var/log/nginx/access.log | awk '{print $1}' | sort | uniq -c | sort -rn | head

# ③ 数据遍历特征：连续递增的 id 参数
grep -oE '[?&](id|uid|order_id|page)=[0-9]+' /var/log/nginx/access.log \
  | sort | uniq -c | sort -rn | head -20

# ④ 非工作时间/异常 UA
grep -vE '(Googlebot|Bingbot|curl)' /var/log/nginx/access.log | tail -200

# ⑤ HTTP 状态码分布（403/401 突增 = 有人在试越权）
awk '{print $9}' /var/log/nginx/access.log | sort | uniq -c | sort -rn
```

### 4.3 内部人员路径（若怀疑内部）

```bash
# 数据库/应用审计日志：谁在什么时候查了什么
#   MySQL 通用查询日志、应用侧操作日志、堡垒机/审计系统日志
mysql -e "SHOW VARIABLES LIKE 'general_log%';"
# ⭐ 重点：单账号在短时间内查询量远超日常（导出行为）
# 终端侧（教材点名的三种植入方式）
#   - U 盘使用记录
#   - 非正规渠道软件安装记录
#   - 钓鱼邮件点击 → 终端木马（见 25-process-service.md / 40-log-analysis.md）
```

> ⭐ **内部路径必须与**服务器管理员 / 业务运营管理员 / 系统开发商**核对**
> （教材 9.2.4 的处置流程就是按"与各方沟通 + 日志分析交叉验证"展开的）：
> 谁能访问数据、有没有独立审计人、有没有关联系统引用同一份数据、服务里有没有硬编码弱密码。

## 五、处置与留证（教材 9.2.4 的九步提炼）

教材用一个"互联网商城订单信息泄露"案例给了完整处置过程，提炼成可执行序列：

| # | 动作 | 要点 |
|---|---|---|
| 1 | 与决策层对齐 | 明确**本次应急要达成的关键目标**，指定接口人 |
| 2 | 梳理网络与防护现状 | 要网络拓扑（哪怕手绘）、服务器区域防护级别、可能入侵路径与难度 |
| 3 | ⭐ **确认日志是否开着，并导出** | 开放的服务/端口是否映射到公网、**系统日志/Web 访问日志/审计日志是否开启**、导出留档 |
| 4 | 梳理**数据权限** | 谁有订单数据访问权、是否有独立审计人、有无关联系统引用同一数据 |
| 5 | 与开发商核对 | 是否做过安全测试、有无**硬编码与弱密码** |
| 6 | 形成初步结论并汇报 | 汇总沟通素材 + 处置经验 |
| 7 | ⭐ **日志全量分析 + 审计人工筛选** | 与第 6 步结论**交叉验证**；若分歧大，回去找有分歧的人再确认 |
| 8 | 定位异常访问 IP | ⭐ 内网 IP → 请运维查**该时段使用人**；外网 IP 且必要时**报案**继续追查 |
| 9 | 编制报告并汇报 | 应急结束 |

⚠️ **第 3 步是最容易翻车的**：如果日志**没开**，那第 7 步无从做起，
报告只能写"因日志未开启，无法确定泄露途径" —— 这本身是重要发现（也是加固建议的依据）。
**所以排查早期一定要先确认日志开着，而不是假定有日志。**

## 六、加固（教材 9.1.3）

按外部/内部两类分别加固：

**对外**
- 供应链：自身供应链系统（物流/仓储/支付）与**第三方供应商**纳入安全评估
- 互联网暴露面：定期搜自己的敏感信息是否出现在**搜索引擎 / 代码仓库 / 网盘 / 社交网络**
- 互联网应用系统：上线前**安全评估**（未授权访问、数据遍历、弱密码、SQL 注入）

**对内**
- 内部人员：最小权限 + **独立审计**（权限与审计必须分离）
- 终端：管控 U 盘、软件来源、钓鱼邮件（终端是"内部泄露"的高频入口）
- 基础支撑平台：ES / Redis / 数据仓库等**必须鉴权 + 不裸奔在内网**
- 内部应用系统：与对外系统同等对待（内部不等于安全）

## 七、常见问法与答法

| 问法 | 答法要点 |
|---|---|
| 数据是怎么泄露的？ | 先分**外部/内部**两大类，再按清单逐条排除。⭐ **先查"公开代码仓库/网盘/搜索收录"** —— 成本最低、命中率高 |
| 怎么判断是外部入侵还是内部人员？ | 教材两条经验判据：数据在**互联网可访问服务器**+未做安全评估 → 偏外部入侵；数据在**内网且仅少数管理员可访问**+内网安全良好 → 偏内部人员。**但要与日志交叉验证，不能只凭这个** |
| 怎么确认数据被取走了多少？ | 靠 **Web 访问日志的批量取数特征**（同 IP 高频访问明细/导出接口、id 递增遍历）+ 应用/数据库审计日志 |
| 日志没开怎么办？ | 如实写"因日志未开启无法确定途径"，并把**日志缺失**本身写进加固建议。**不要编一条路径出来** |
| 能追到人吗？ | 内网 IP → 请运维查**该时段使用人**；外网 IP → **报案**后由有关部门继续追查。别在报告里指认个人 |
| 要不要通知外部？ | 涉及**大量个人隐私数据**时有监管通报/合规义务 —— 这超出技术排查范围，但报告里要提示 |

## 八、⚠️ 表述纪律（这类事件最容易越界）

| 该说 | 不该说 |
|---|---|
| "[观测] 某 IP 在 3 小时内访问 `/api/order/detail` 12,000 次" | "某 IP 窃取了 12,000 条订单"（**取了多少条 ≠ 访问了多少次**） |
| "[推断] 该 IP 行为符合数据遍历特征" | "攻击者是内部人员"（无证据的指认） |
| "[观测] 代码仓库中存在含数据库连接串的文件（提交于 X 日）" | "研发泄露了数据"（**存放 ≠ 泄露**，需证明被外部访问） |
| "[观测] 对象存储匿名可读" | "数据已被下载"（可读是**风险**，下载才是**事件**） |

⭐ 这类事件的报告常被用于**对外通报与责任认定**，所以措辞比技术判断更需要克制。
